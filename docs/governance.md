# Контроль качества и защита репозитория

Status: accepted

## Три разных уровня

Инструкции объясняют поведение; `make check` проверяет исполняемые ограничения;
активная защита ветки запрещает merge без необходимых результатов.
Ни один уровень отдельно не гарантирует безошибочное поведение любого агента.

## Фактический статус

На 2026-09-11 GitHub API подтвердил активный ruleset `main-quality`, ID `22904369`,
для `refs/heads/main`. Требуются PR, успешный check `quality` на актуальной базе и
разрешение review threads; удаление и force push запрещены. Список bypass actors пуст,
текущий пользователь не может обходить правила (`current_user_can_bypass: never`).
Источник: [состояние ruleset](https://api.github.com/repos/Gorills/sloi-game/rulesets/22904369).
Настройки могут изменяться: проверять API перед merge, а не доверять только этой записи.

В foundation защита ещё не была включена; при публикации графического этюда её наличие
подтверждено повторным чтением. Этот PR обновляет запись, а не меняет правила GitHub.
Файл [main-ruleset.json](../.github/main-ruleset.json) остаётся исходным шаблоном.

Для одного владельца число обязательных approvals — 0, иначе автор PR не сможет
одобрить собственную работу. Это не независимое review. Когда появится отдельная
bot identity/второй reviewer, рассмотреть обязательное owner review отдельным решением.

## Повторная проверка защиты

В GitHub Settings → Rules → Rulesets либо через API сверить область `main`,
check context `quality`, enforcement `Active` и список bypass actors.
Операция в настройках не выполняется автоматически workflow с повышенными правами.
Не проверять защиту разрушительным force push реального main. Наличие конфигурации
и успешный CI сами по себе не являются отдельным негативным тестом блокировки merge.

## Что проверяется автоматически

Размер исходников/функций, TS strict/запрет explicit any, структура навыков,
локальные ссылки и индексирование документов, отсутствие рукописей/БД, Ruff,
unit/integration, браузерный каталог и локальная сцена. Тесты самих ограничений содержат отрицательные примеры.
Для новой игры требуются новые поведенческие тесты; существующий зелёный каталог их не заменяет.

## Что требует review

Связность модулей, соответствие канону, ценность механики, удобство, безопасность
авторизации и корректность утверждений о выполненных проверках.
Изменения AGENTS, навыков, workflow, лимитов и исключений требуют отдельного обоснования.
Администратор может изменить защиту; текстовый файл не является security boundary.
