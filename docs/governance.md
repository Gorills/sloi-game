# Контроль качества и защита репозитория

Status: accepted

## Три разных уровня

Инструкции объясняют поведение; `make check` проверяет исполняемые ограничения;
активная защита ветки запрещает merge без необходимых результатов.
Ни один уровень отдельно не гарантирует безошибочное поведение любого агента.

## Фактический статус

При подготовке foundation GitHub API вернул пустой список repository rulesets.
Доступный коннектор позволяет создавать коммиты/ветки/PR, но не предоставляет операции
активации ruleset. Поэтому **защита main этим PR не включена**.
Шаблон [main-ruleset.json](../.github/main-ruleset.json) подготовлен, не применён.
Не описывать его наличие как действующий запрет direct push.

Шаблон требует PR, успешный check `quality` на актуальной базе, разрешённые review threads,
запрещает удаление/force push. Для одного владельца число обязательных approvals — 0,
иначе автор PR не сможет одобрить собственную работу. Это не независимое review.
Когда появится отдельная bot identity/второй reviewer, включить обязательное owner review.

## Активация владельцем

В GitHub Settings → Rules → Rulesets импортировать JSON и проверить область `main`,
check context `quality`, enforcement `Active` и отсутствие ненужных bypass actors.
Операция в настройках не выполняется автоматически workflow с повышенными правами.
После активации зафиксировать ID/настройки и проверить, что PR с падающим check не mergeable.
Не проверять защиту разрушительным force push реального main.

## Что проверяется автоматически

Размер исходников/функций, TS strict/запрет explicit any, структура навыков,
локальные ссылки и индексирование документов, отсутствие рукописей/БД, Ruff,
unit/integration и браузерный каталог. Тесты самих ограничений содержат отрицательные примеры.
Для новой игры требуются новые поведенческие тесты; существующий зелёный каталог их не заменяет.

## Что требует review

Связность модулей, соответствие канону, ценность механики, удобство, безопасность
авторизации и корректность утверждений о выполненных проверках.
Изменения AGENTS, навыков, workflow, лимитов и исключений требуют отдельного обоснования.
Администратор может изменить защиту; текстовый файл не является security boundary.
